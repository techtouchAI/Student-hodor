# سياسة توقيع الإصدار (لماذا لا يجوز أن يتغيّر المفتاح)

## القاعدة الذهبية

على أندرويد، **هوية التطبيق = معرّف الحزمة + مفتاح التوقيع**. أي حزمة جديدة
موقّعة بمفتاح مختلف عن المثبّت:

- لا تُثبَّت فوقه (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`)؛
- وإن حذف المستخدم التطبيق خسر قاعدة البيانات المحلية، واسترجاعها رهين وجود
  نسخة احتياطية.

لذلك: **مفتاح التوقيع أصلٌ من أصول المشروع**، يُحفظ ويُنقل بعناية، ولا يُعاد
توليده «عند الحاجة».

## ما كان يحدث قبل هذا المستند (سبب الأعطال الميدانية)

1. سير العمل كان يولّد مفتاحاً جديداً صامتاً إن غاب ملف المفتاح
   (`Bootstrap release keystore if absent`) ⇒ كل بناء بمفتاح مختلف.
2. و`build.gradle` كان يرجع إلى **مفتاح التصحيح** إن غاب مفتاح الإصدار، ويسمّي
   الناتج `app-release.apk` ⇒ حزمة «إصدار» لا تُثبَّت فوق نسخة الميدان.
3. والنتيجة: أول حزم نُشرت (2026‑09‑15 قبل تثبيت المفتاح في المستودع) موقّعة
   بمفاتيح مرحلية. كل جهاز ثبّت واحدة منها لا يقبل أي تحديث لاحق.

## الوضع بعد الإصلاح (فشل صريح لا صامت)

| الحالة | السلوك |
|---|---|
| سرّ `KEYSTORE_BASE64` مضبوط | يُفكّ ترميزه إلى `tools/keystore/student_hodor.jks` ويُستخدم |
| لا سرّ، والملف موجود في المستودع | يُستخدم مع تحذير في السجل (مسار تطويري) |
| لا سرّ ولا ملف | **إخفاق صريح** للبناء برسالة تشرح السبب |
| بناء إصدار بلا مفتاح | مهمة `checkReleaseSigningKey` تفشل ولا يُنتَج APK |

مخططات التوقيع مُعلنة صراحةً في `build.gradle`: `v1` (لتوافق مثبّتات بعض
الأجهزة وأنظمة MDM المدرسية)، و`v2` (إلزامي منذ أندرويد 7.0)، و`v3` (يسمح
بدوران المفتاح مستقبلاً عبر `apksigner rotate` بلا كسر التحديثات).

## قبل كل إصدار

ارفع `versionCode` في `pubspec.yaml` (الرقم بعد `+`). القاعدة آلية: البوابة
ترفض نشر حزمة رقمها مساوٍ أو أصغر من المنشور، لأن أندرويد يرفض التحديث
التنازلي — وكل حزمة منشورة تُعدّ «إصداراً» وإن كانت إعادة بناء بلا تغيير كود.

## بوابة النشر تمنع تكرار الكارثة

قبل النشر، `tools/verify_apk.py gate` يقارن الحزمة الجديدة بالمنشورة فعلياً
على وسم `latest-apk`، ويرفض النشر إن:

- اختلفت بصمة شهادة التوقيع (`SIGNING_KEY_ROTATED`)؛
- لم يزدد `versionCode` (`VERSION_CODE_NOT_INCREASED`)؛
- تغيّر معرّف الحزمة (`PACKAGE_ID_CHANGED`)؛
- ارتفع `minSdk` (`MIN_SDK_INCREASED`) — أي رفع جديد يلزمه تجاوز صريح
  (`--allow-minsdk-bump`) مع إعلانه في ملاحظات الإصدار؛
- فشل التحقق من الحزمة نفسها: سلامة الأرشيف، `apksigner`، محاذاة 16KB
  للمكتبات الأصلية 64‑بت، أو وجود صلاحية مخالفة لعقد الأوفلاين.

## نقل المفتاح إلى أسرار المستودع (موصى به)

المفتاح الخاص مرفق حالياً بالمستودع لاستمرار البناء. المستودع **عام**، وأي
شخص يملكه يستطيع توقيع تحديث خبيث يُثبَّت بسلاسة فوق تطبيق المدارس. الخطوات:

```bash
# 1) أنشئ السرّ من المفتاح الحالي (base64 سطر واحد)
base64 -w0 tools/keystore/student_hodor.jks > /tmp/key.b64
gh secret set KEYSTORE_BASE64 < /tmp/key.b64
gh secret set KEYSTORE_STORE_PASSWORD -b "studenthodor"
gh secret set KEYSTORE_KEY_ALIAS      -b "student_hodor"
gh secret set KEYSTORE_KEY_PASSWORD   -b "studenthodor"

# 2) احذف المفتاح من Git (يظل محلياً لديك وفي السرّ)
git rm --cached tools/keystore/student_hodor.jks

# 3) احذف سطر الاستثناء من .gitignore (*.jks يكفي) وثبّت التغيير
```

بعد ذلك يعمل البناء من السرّ وحده. **احتفظ بنسخة من المفتاح خارج المستودع
(خزنة/قرص مشفّر):** ضياعه يعني نهاية سلسلة التحديثات.

## للتوزيع الرسمي لاحقاً

إن أردت النشر على متجر Google Play: فعّل **Play App Signing** واحتفظ بمفتاح
الرفع (upload key) فقط. حينها يستضيف جوجل مفتاح التوزيع، وفقدان مفتاح الرفع
قابل للاستعادة — وهو أفضل من التوزيع اليدوي متى سمحت بيئة المدارس بذلك.
