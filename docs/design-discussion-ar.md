## 1) التعارضات والمشاكل التقنية (يجب حسمها قبل كتابة أي سطر كود)

### 1.1 تعارض جوهري: ماذا يُخزَّن داخل الباركود؟
فكرتك تقول: «توليد باركود خاص باسم كل طالب والصف والشعبة والمدرسة». هذا يصطدم بأربع مشاكل:

| المشكلة | التفصيل |
|---|---|
| كثافة الرمز | الاسم العربي الكامل + الصف + المدرسة داخل Code128 = شريط طويل جداً وكثيف يفشل قارئ الموبايل بقراءته من مسافة natural. حتى QR يصبح كثيفاً وبطيء الفكّ. |
| تغيّر البيانات | إذا انتقل الطالب لشعبة أخرى أو صُحِّح خطأ إملائي في اسمه → الباج القديم يصبح «بياناته قديمة» ويجب reprint لكل الطلاب المتأثرين. |
| تشابه الأسماء | طالبان بنفس الاسم بنفس الصف (شائع جداً) → الباركود الاسمي لا يميّزهما. |
| الخصوصية | باركود يحمل الاسم الكامل يعني أي شخص يصوّر الباج يحصل على اسم الطالب مقروءاً آلياً. |

**الحل المقترح (مع الحفاظ على روح فكرتك):** الباج *يعرض* الاسم الكامل والصف والشعبة والمدرسة كنص مطبوع واضح (كما طلبت)، لكن الباركود/QR نفسه يحمل **رقماً تسلسلياً ثابتاً + رمز تحقق (checksum)** فقط، وعند القراءة يجلب التطبيق الاسم والصف من قاعدة البيانات لحظياً. النتيجة: قراءة أسرع وأدق، نقل طالب بين الشعب لا يبطل باجه، ولا لبس بين الأسماء المتشابهة.
صيغة الرمز المقترحة: `SH-{رمز المدرسة}-{رقم الطالب}-{سنة قصيرة}-{checksum}` مثال: `SH-NJR-0042-26-K7`.

### 1.2 باركود خطي (Code128) أم QR؟
- Code128 الخطي: رفيع، حساس للزاوية والاهتزاز والإضاءة، وتفشل كاميرات الموبايل معه كثيراً عند الطباعة الصغيرة.
- QR: منطقة تحمل خطأ (Error Correction) تتحمل الخدش والانحناء والإضاءة السيئة، ويُقرأ بزاوية، ويدعم الأرقام/العربي.
- ملاحظة توافق: متصفح Chrome/Android وSafari 17+ يدعمان API أصلي للقراءة، مع مكتبة WASM احتياطية للمتصفحات الأخرى — سنغطي الاثنين.

**التوصية:** QR هو الرمز الأساسي الذي تقرأه الكاميرا، مع شريط Code128 ثانوي أسفل الباج (للطابع/القارئ الليزري إن وُجد لدى الإدارة، ولمظهر رسمي). التطبيق يقرأ الصيغتين معاً تلقائياً.

### 1.3 «الغياب = من لم يُقرأ باركوده» — تعريف ناقص خطراً
بهذا التعريف، كل يوم لا تُجرى فيه عملية مسح (عطلة، امتحانات، يوم لم يُفتح التطبيق) سيتحول تلقائياً إلى «كل الطلاب غائبون»! وحتى أيام الجمعة ستُسجّل غياباً.
**الحل الإلزامي — تقويم أيام الدوام:**
1. إعدادات: أيام الدوام الأسبوعية (مثلاً الأحد–الخميس) + جدول العطل الرسمية قابل للتعديل.
2. زر «بدء حصة/طابور» وزر «إنهاء وإقفال اليوم»: عند الإقفال يتحول كل طالب لم يُقرأ رمزُه في ذلك اليوم إلى «غائب» تلقائياً، وما قبل الإقفال يبقى «قيد الانتظار».
3. الأيام المغلقة فقط تدخل في التقارير والإحصاء — لا غياب في يوم غير مقفول أو عطلة.

### 1.4 الباج المشترك / القراءة بالنيابة (ثغرة فكرية في النظام كله)
طالب يصوّر باج صديقه الغائب ويرسل الصورة، وصديقه الحاضر يمسحها → غياب غير مرصود. لا يوجد حل تقني 100% بدون بصمة/وجه، لكن نخفضها كثيراً:
- صورة الطالب على الباج (يراه المعلم أثناء المسح) — أقوى رادع عملي.
- منع التكرار: قراءة ثانية لنفس الرمز بنفس اليوم = رفض + تنبيه صوتي/اهتزاز مختلف.
- سجل زمني دقيق لكل قراءة؛ قراءتان متتاليتان بفارق ثوانٍ لرمزين مختلفين = علامة تدقيق.
- نافذة زمنية قبول للمسح (ساعة الطابور) قابلة للضبط، وما بعدها يُعلَّم يدوياً.
- مراجعة يومية: قائمة «غير المقروءين» تظهر للمعلم فور الإقفال ليؤكد أو يصحح.

### 1.5 «تصفير عداد الغيابات» vs «إغلاق السنة الدراسية»
فكرتك: خياران عند نهاية السنة (تصفير العداد مع إبقاء الأسماء، أو تصفير كامل). المشكلة: تصفير العداد *يمحو* سجل سنة كاملة قد تُطلب قانونياً أو من ولي الأمر، ويكسر «تخزين نتائج حضور وغياب لكل طالب على مدار السنة» المذكور في طلبك نفسه.
**النموذج المقترح — سنوات متعددة:**
- كل سنة دراسية كيان مستقل بسجلاتها وبادجاتها (رمز الباج يحتوي السنة).
- زر «إنهاء السنة الحالية»: يؤرشف السنة (قراءة فقط، تقاريرها تبقى متاحة)، يرقّي الطلاب للصف التالي تلقائياً بأداة ترقية، ويبقي الأسماء — وهذا هو بالضبط «تصفير العداد مع إبقاء الأسماء» لكن بدون فقدان التاريخ.
- زر «تصفير شامل» يبقى موجوداً كخيار منفصل *خطر*: يتطلب تأكيداً كتابياً + تنزيل نسخة احتياطية إجبارية قبل التنفيذ.
- تقرير «مسيرة الطالب» يجمع سنواته كلها إن رغبت الإدارة.

### 1.6 أين تعيش البيانات؟ (أهم قرار معماري)
المسح يتم بموبايل المعلم، والإدارة تريد التقارير من جهاز المكتب. ثلاثة مسارات:

| الخيار | الوصف | المزايا | العيوب |
|---|---|---|---|
| A — تطبيق ويب (PWA) + خادم محلي | سيرفر صغير (Python/FastAPI + SQLite) على جهاز الإدارة، والموبايلات تتصل عبر واي فاي المدرسة؛ وضع Offline بقائمة مزامنة | قاعدة واحدة لكل المعلمين، تقارير مركزية، تحديث للجميع فوراً | يحتاج تشغيل السيرفر وشبكة داخلية + HTTPS للكاميرا (نحلها بشهادة محلية/نفق) |
| B — متصفح فقط بدون سيرفر | موقع ثابت، البيانات في IndexedDB على الجهاز | يعمل فوراً وبأبسط نشر، مناسب لمعلم واحد/جهاز واحد | البيانات لكل جهاز منفصلة؛ المزامنة يدوية عبر ملفات نسخ |
| C — تطبيق Android أصلي (Flutter) | أفضل تحكم بالكاميرا ونشر عبر APK | تكلفة تطوير وصيانة أعلى بكثير، كاميرا ويب أسهل للتجربة الآن |

**التوصية:** A مع بناء الطبقة البياناتية بحيث يعمل B كوضع تلقائي عند عدم وجود سيرفر (Offline-first).

### 1.7 الكاميرا تحتاج HTTPS (قيد متصفحات لا يمكن تجاوزه)
كاميرا الموبايل من المتصفح لا تعمل إلا عبر HTTPS أو localhost. على شبكة مدرسة这意味着: شهادة TLS محلية مولّدة تلقياً + تثبيتها على الأجهزة، أو نفق آمن، أو تشغيل التطبيق كـPWA مثبّت. سنجهّز سكربت إعداد للشبكة الداخلية ضمن المشروع.

### 1.8 العربية في ملفات Excel وPDF (فخ klassيكي)
- **Excel:** النص العربي يُحفظ صحيحاً، لكن يجب ضبط اتجاه الورقة RTL واتجاه الخلية (readingOrder) وإلا ظهرت الأسماء محاذية لليسار بشكل مشوّه؛ التلوين (أخضر/أحمر/أصفر) مدعوم بالكامل عبر openpyxl/ExcelJS.
- **PDF:** المشكلة الشهيرة — حروف عربية متقطعة/معكوسة إن وُلّد الملف بمكتبة naïve. الحل المعتمد: توليد PDF من صفحة HTML عبر محرك متصفح (Playwright/Chromium) أو WeasyPrint + خط عربي TTF مضمّن (Amiri) → عربي سليم 100% + ألوان + جداول + ترويسة رسمية بتوقيع المدير.
- أسماء الأشهر والأرقام: خيار عربي/إنجليزي للأشهر، وأرقام عربية أو لاتينية بال إعدادات.

### 1.9 طباعة الباجات — مقاسات حقيقية
- مقاسان مطلوبان: CR80 (85.6×54mm) لطابعات البطاقات PVC، وورقة A4 عليها 8 أو 10 باجات للطابعات العادية مع علامات قص وثقب الحبل.
- التصميم بدقة 300dpi، منطقة أمان للقطع، وموضع ثابت لثقب التعليق.
- تصدير دفعي: PDF واحد فيه كل باجات صف/مدرسة مرتبة، + معاينة PNG فردية.
- طول الاسم: أسماء رباعية/خماسية طويلة → خوارزمية تصغير خط/التفاف تلقائي داخل صندوق الاسم حتى لا يكسر التصميم.

### 1.10 تطبيع الأسماء ومنع التكرار
«أحمد» vs «احمد»، تشكيل، تطويل، مسافات مزدوجة، همزات → تكرارات وهمية أو طالب مكرر مرتين. الحل: تطبيع تلقائي عند الحفظ + تحذير «يوجد اسم مشابه بنفس الصف» + قيد فريد (الاسم المطبّع + الصف + الشعبة).

### 1.11 هل الحالات الثلاث كافية؟ (حضور/غياب/إجازة)
الواقع المدرسي يحتوي: **متأخر**، خروج مبكر، غياب بعذر/بدون عذر. الألوان الثلاثة تبقى كما طلبت (أخضر/أحمر/أصفر)، لكن أقترح إضافة «متأخر» كحالة رابعة بلون برتقالي تُحتسب حضوراً ناقصاً في النسبة — قرار لك.

### 1.12 من يفتح التطبيق؟ (صلاحيات)
بدون أي حماية: أي طالب يمسك جهاز المكتب يستطيع «تصفير البيانات». الحد الأدنى: PIN/كلمة مرور للمدير + حساب معلم (مسح وتصحيح فقط) + سجل تدقيق (من غيّر حالة من ومتى). التقارير والطباعة تبقى للجميع أو تُقيّد — قرار لك.

## 2) إضافات مهمة أغفلها الطلب (أقترح ضمها للنطاق)

1. **إدخال يدوي احتياطي:** نسي الطالب باجه/تلف → بحث بالاسم وتسجيل حضور؛ وزر «تحضير الصف كاملاً» ثم استثناء الغائبين (أسرع من مسح 40 باجاً عند ضيق الوقت).
2. **إدارة إجازات كاملة:** إجازة بتاريخ بداية/نهاية + نوع (مرضیة/عرضية/طارئة) + سبب + مرفق اختياري؛ تُلوَّن أيامها أصفر تلقائياً وتظهر في تقرير الطالب.
3. **جدول عطل رسمية** قابل للتعديل يدوياً (دينية/وطنية) + أيام الأسبوع الدراسية.
4. **إنذار مبكر:** نسبة حضور لكل طالب، عدّاد أيام الغياب المتتالية، وقائمة «طلاب تجاوزوا حد الإنذار» بنسبة قابلة للضبط (مثلاً إنذار عند 10% وحرمان عند 15%) — من أكثر ما تحتاجه الإدارة فعلياً.
5. **تقرير فردي للطالب:** تقويم شهري ملوّن (heatmap) + مجاميع + نسبة + خانة توقيع المدير؛ قابل للطباعة ككتاب رسمي لولي الأمر.
6. **صورة الطالب على الباج:** ترفع الاحترافية وتمنع القراءة بالنيابة؛ التقاط من كاميرا الموبايل أو رفع ملف (اختياري لكل طالب).
7. **إصدار بدل فاقد:** إبطال باج قديم وإصدار نسخة جديدة برقم نسخة جديد، حتى لا يُستخدم الباج المفقود.
8. **نسخ احتياطي واسترجاع:** تلقائي يومي + زر يدوي + استرجاع من ملف؛ سنة كاملة من العمل لا يجب أن تضيع بفقدان جهاز.
9. **استيراد جماعي للطلاب** من Excel/CSV (اسم، صف، شعبة) بدل الإدخال الفردي، وتصدير قائمة الطلاب.
10. **إدارة صفوف وشعب وأقسام** + أداة ترقية جماعية نهاية السنة.
11. **بنية تحتية للحصص:** جدول attendance يدعم session_id منذ اليوم الأول، فإن أرادت المدرسة لاحقاً حضوراً لكل حصة لا نعيد بناء قاعدة البيانات.
12. **تاريخ هجري اختياري** بجانب الميلادي في التقارير والبادجات.
13. **واجهة RTL كاملة** بأزرار ضخمة لشاشة المسح (تُستخدم واقفاً أمام الصف)، زر فلاش، اهتزاز+صوت عند النجاح، ومنع نوم الشاشة أثناء المسح.
14. **الأداء:** 1000 طالب × ~200 يوم = 200 ألف سجل — SQLite يفهرسها بسهولة؛ التصدير الدفعي يُبث stream ولا يُحمّل بالذاكرة.

## 3) Architecture المقترحة (بعد حسم القرارات)

- **الخيار A الموصى به:** PWA ويب (واجهة عربية RTL) + خادم Python/FastAPI + SQLite، طبقة بيانات تعمل Offline-first في المتصفح أيضاً.
- **Excel:** openpyxl (خلفية) / ExcelJS (متصفح) مع RTL وتلوين الخلايا وتكرار صف العناوين وتجميدها.
- **PDF:** HTML→PDF عبر Chromium/Playwright بخط عربي مضمّن.
- **الباركود:** QR (أساسي) + Code128 (ثانوي) بمكتبة توليد محلية، مع checksum.
- **نموذج البيانات المبدئي:**
  `school_settings, academic_years, grades, sections, students, student_photos, badges(version,status), weekdays_config, holidays, scan_events(log), attendance_daily(student,date,status,source), leaves, users, audit_log`
- **مراحل التنفيذ المقترحة:**
  1. الإعداد الأولي (مدرسة/مدير/سنة) + صفوف وطلاب + توليد الباجات (PDF/PNG) بالتصميم المعتمد.
  2. شاشة المسح بالكاميرا + الحضور اليومي + الإدخال اليدوي + إقفال اليوم.
  3. التقويم والعطل والإجازات + التقارير والإحصاء والإنذار المبكر.
  4. تصدير Excel/PDF بخيارات الأشهر والألوان كما وصفت.
  5. إنهاء السنة/الترقية/التصفير + النسخ الاحتياطي + الصلاحيات + الإعدادات.
  6. تحسينات: صور الطلاب، بدل فاقد، إشعارات ولي الأمر.

## 4) أسئلة تحتاج قرارك (أجاباتها تحدد البداية)

1. المنصة: A (ويب+سيرفر مدرسي) أم B (متصفح فقط) أم C (Android أصلي)؟
2. توافق على QR أساسي + Code128 ثانوي؟ أم条码 خطي فقط؟
3. توافق على أن يحمل الرمز رقماً ثابتاً (لا الاسم) مع بقاء الاسم مطبوعاً على الباج؟
4. أيام الدوام (افتراض: الأحد–الخميس) والدولة لجدول العطل (افتراض: العراق)؟
5. هل نضيف حالة «متأخر» برتقالية أم نكتفي بالثلاث؟
6. صورة الطالب على الباج: من الإصدار الأول أم لاحقاً؟
7. مدرسة واحدة أم عدة مدارس بنفس التثبيت؟
8. عدد الطلاب التقريبي (لاختيار تنسيق A4 وعدد الباجات بالورقة)؟
9. هل مطلوب حد غياب نظامي (إنذار/حرمان) بنسبة قابلة للضبط؟
10. الواجهة عربية فقط أم عربية/إنجليزية؟

> بعد ردك على هذه النقاط (يكفي جواب مختصر بالأرقام) أبدأ التنفيذ مباشرة بالمرحلة 1.

# الملحق الأول: قرار «تطبيق أندرويد + أوفلاين تماماً + قاعدة بيانات محلية» — تعارضاته وحلوله

تم اعتماد قرارك: تطبيق أندرويد، عمل أوفلاين 100%، قاعدة بيانات محلية على الجهاز بدون أي اتصال بالإنترنت.
هذا القرار سليم وممكن تقنياً، لكنه يولّد تعارضات جديدة يجب أن تراها قبل البدء:

## 5.1 تعارض ملكية البيانات: من الجهاز الذي يحمل «الحقيقة»؟
أوفلاين كامل = لا خادم يوحّد البيانات. إذا مسح معلمٌ من هاتفه ومعلمة من هاتفها → قاعدتا بيانات متباعدتان لا يلتقيان أبداً.
**الحل المعتمد:**
- تعريف «جهاز الحضور الرسمي» (جوال/تابلت المدرسة) كمرجع أساسي.
- أداة **دمج جلسات**: أي جهاز ثانوي يصدّر ملف جلساته، والجهاز الرسمي يستورده ويدمجّه بمنع التكرار (مفتاح الدمج: الجلسة+التاريخ+رقم الطالب).
- سؤال لك: كم جهاز سيمسح فعلياً عندك؟ (يحدد أولوية أداة الدمج).

## 5.2 توزيع APK وتحديثه بدون متجر
- التثبيت يدوي (ملف APK)، والتحديث = تثبيت إصدار أحدث **بنفس التوقيع** → بيانات المدرسة تبقى تلقائياً.
- التزام هندسي: هجرات تلقائية لبنية قاعدة البيانات عند أول تشغيل لكل إصدار جديد، وعدم تغيير مدمّر أبداً بدون تصدير إجباري مسبق.
- البناء والنشر: مستودع المشروع على GitHub وأداة gh موصولة → **GitHub Actions يبني APK موقّعاً لكل إصدار وينشره كـ Release** جاهز للتنزيل (بيئة العمل المحلية لا تحتوي Android SDK، لكن.runners الخاصة بـGitHub تحتويه كاملاً).

## 5.3 النسخ الاحتياطي يصبح مسؤولية مصيرية
لا سحابة تعوّض فقدان الجهاز. لذا: نسخ احتياطي تلقائي يومي كملف واحد داخل تخزين الجهاز + تذكير قوي إن مرّت 7 أيام بدون نسخ + تصدير إجباري قبل أي عملية تصفير/حذف + استرجاع بزر واحد.

## 5.4 تقنية المسح بالكاميرا أوفلاين
- داخل APK: ماسح **MLKit الأصلي** (نموذج التعرف مضمّن داخل الـAPK نفسه → يعمل بلا إنترنت إطلاقاً، سريع ومعتمد في الإضاءة الضعيفة).
- في نسخة المعاينة الفورية بالمتصفح: API الكاميرا الأصلي للمتصفح (BarcodeDetector) كبديل بدون مكتبات.
- الصيغتان معاً: QR (أساسي) + Code128 (ثانوي).

## 5.5 العربية في Excel وPDF على الجهاز نفسه
- **Excel:** مكتبة ExcelJS مضمّنة داخل التطبيق → تلوين الخلايا (أخضر/أحمر/أصفر/برتقالي)، اتجاه RTL، تجميد وتكرار رؤوس، وملف .xlsx حقيقي يفتح سليماً على أي جهاز.
- **PDF:** يُولّد عبر محرك طباعة أندرويد (Chromium) → عربية سليمة 100% بدون مشاكل تشكيل الحروف، مع خيار «حفظ كـPDF» أو الإرسال لطابعة مباشرة.
- **الباجات:** تصميم HTML بدقة 300dpi يُحوّل إلى PDF طباعة: ورقة A4 عليها 8 أو 10 باجات مع علامات قص، أو مقاس CR80 لطابعات البطاقات.

## 5.6 قاعدة البيانات المحلية: التقنية المختارة
طبقة بيانات موحّدة فوق **IndexedDB داخل التطبيق** (مخزن دائم داخل مساحة التطبيق على أندرويد، يبقى بعد إغلاق التطبيق وتحديثه)، بمخطط جداول علائقي واضح + هجرات إصدارات + ملف نسخ احتياطي واحد للاسترجاع والدمج.
لماذا ليست SQLite أصلية؟ لأن ذلك يتطلب إضافة أصلية مختلفة بين نسخة المعاينة والـAPK، بينما الطبقة الموحّدة تعطي نفس الكود والسلوك في الاثنين، وملف النسخ الاحتياطي هو ضمان النقل بين الأجهزة. (بنية الجداول نفسها قابلة للنقل لـSQLite لاحقاً إن رغبت.)

## 5.7 ساعة الجهاز = تاريخ الحضور
أوفلاين يعني أن تاريخ الجهاز هو المرجع الوحيد. لذا: عرض التاريخ واليوم بارزين أعلى شاشة المسح، وتحذير فوري إن كان التاريخ خارج نطاق السنة الدراسية الفعّالة أو إن اختلف عن آخر جلسة مسجلة.

## 5.8 شاشة المسح ميدانياً
منع نوم الشاشة أثناء المسح، زر فلاش، اهتزاز+نغمة نجاح/رفض مختلفة، وأزرار ضخمة — كلها واجهات أصلية عبر Capacitor بدون إنترنت.

## 5.9 ما الذي يخسره وضع الأوفلاين فقط (وبديله)
- لا لوحة متابعة حية للمدير من مكتبه → البديل: تقرير يومي/أسبوعي ملفاً أو طباعة.
- لا إشعار فوري لولي الأمر → البديل: كتب غياب/إنذار PDF جاهزة للطباعة أو المشاركة.
- أكثر من مدرسة = إما تثبيت منفصل أو قاعدة واحدة بمبدّل مدارس (اعتمدنا الثاني، انظر D6).

## 7) خطة التنفيذ بعد أمر البدء (بنية Capacitor + ويب)

- **النواة:** تطبيق ويب عربي RTL (Vite + TypeScript) يعمل داخل غلاف أندرويد عبر Capacitor — نفس الكود = نسخة المعاينة والـAPK.
- **المراحل:** (1) إعداد مدرسة/مدير/سنة + صفوف وطلاب + توليد الباجات وطباعتها. (2) شاشة المسح MLKit + الحضور اليومي + الإدخال اليدوي + إقفال اليوم. (3) التقويم والعطل والإجازات + التقارير والإنذار المبكر. (4) تصدير Excel/PDF بخيارات الأشهر والألوان. (5) إنهاء السنة/الترقية/التصفير + النسخ + الصلاحيات(PIN) + الإعدادات. (6) صور الطلاب، بدل فاقد، دمج الأجهزة، كتب أولياء الأمور.
- **التسليم:** كود كامل على الفرع الحالي + APK مبني عبر Actions + دليل استخدام عربي مصوّر داخل التطبيق.

# الملحق الثاني: تحليل Flutter + Dart Native — بناء APK كامل واحترافي ومتوافق (القرار النهائي المعتمد)

بناءً على قرارك الأخير: **تطبيق Flutter/Dart أصلي لأندرويد، أوفلاين 100%، قاعدة بيانات محلية، وbuild احترافي متوافق**. سحبنا مقترح Capacitor نهائياً. هذا التحليل يعيد دراسة كل شيء وفق المعطيات الجديدة.

## 10.1 معطيات البيئة الحاكمة (حقائق مؤكدة بالفحص)
- بيئة العمل المحلية: لا Flutter SDK ولا Java/Android SDK، ولا وصول لشبكات pub.dev/storage.googleapis/dl.google → **كل بناء APK يتم عبر GitHub Actions** (الـrunners تحتوي Flutter قابلة للتثبيت + Android SDK كامل + شبكة).
- المستودع **خاص** ✓ → حل التوقيع المستقر ممكن داخل المستودع نفسه (انظر K1).
- توكن الـbot لا يملك صلاحية إدارة Secrets (403 مؤكدة) → لن نعتمد على Secrets في أي شيء حرج.
- تطوير محلياً = كود + تحليل ذهني صارم؛ كل ترجمة واختبار عبر CI عند كل push (دورة 5–10 دقائق لكل دورة بناء).

## 10.2 المعارك التقنية الأربع في Flutter وحلولها الاحترافية

### المعركة أ — العربية في ملفات PDF (الأخطر، مؤكدة: حزم pdf/printing لا تشكّل العربية)
بدون حل ستخرج الحروف **مقطعة** في كل تقرير PDF. الاستراتيجية الهرمية المعتمدة (Arabic Pipeline):
1. **الباجات والبطاقات والتقارير الفردية:** تُبنى كـFlutter widgets ثم تُحوَّل لصورة بدقة 300dpi عبر `Picture.toImage/RepaintBoundary` وتُضمَّن في الـPDF → عربية مثالية بحكم محرك Flutter نفسه، مع حرية تصميم كاملة وظلال وحدود — صفر مخاطرة تشكيل.
2. **الجداول متعددة الصفحات (كشف الشهر/السنة):** وحدة تشكيل عربية **داخل المستودع** (Dart port لخوارزمية python-arabic-reshaper المعروفة + ترتيب Bidi) مع unit tests تغطي: اتصال الحروف، لام-ألف، التشكيلOptional، الأرقامMixed، أسماء طويلة. لا نعتمد حزمة pub.dev المسماة arabic_reshaper لأنها v0.0.1 بناشر غير موثّق ومئات التنزيلات فقط = مخاطرة غير مقبولة في بناء «احترافي».
3. **شبكة أمان تلقائية:** أي صفحة جدول تفشل verifica­tion التشكيل تُrender صورتياً (rast­er) تلقائياً بدل إصدار نص معطوب — المستخدم لن يرى عربياً مكسوراً أبداً.
4. خط TTF عربي (Amiri) مضمّن في assets للعمل أوفلاين.

### المعركة ب — Excel ملوّن RTL: محسومة ومؤكدة
حزمة `excel` تدعم أصلاً: `backgroundColorHex` (أخضر/أحمر/أصفر/برتقالي)، حدود، محاذاة، التفاف، و`sheet.rtl = true` باتجاه الورقة كاملة. أي ميزة OOXML ناقصة (تجميد صفوف/تكرار رؤوس عند الطباعة) تُضاف بـpost-process patch آمن على ملف الـzip الناتج داخل المستودع + اختبار CI يفك الملف ويتحقق من الـXML.

### المعركة ج — المسح بالكاميرا أوفلاين: محسومة
حزمة `mobile_scanner` (Google MLKit bundled): نموذج التعرف **داخل الـAPK** بلا إنترنت، يقرأ QR وCode128 معاً، مع torch وzoom وauto-stop. بديل دائم: إدخال يدوي/بحث بالاسم.

### المعركة د — قاعدة البيانات المحلية: ارتقاء عن الخطة السابقة
`drift` (ORM فوق SQLite أصلية): ملف `.db` حقيقي داخل مساحة التطبيق، جداول typed، **migrations مترقّمة** تلقائية عند تحديث النسخة، واستعلامات مفهرسة (200 ألف سجل بلا تأخير). ملف الـ.db نفسه هو وحدة النسخ الاحتياطي والدمج بين الأجهزة. هذا يحقق حرفياً طلبك «قاعدة بيانات محلية» أفضل من أي مخزن متصفح.

## 10.4 خط البناء الاحترافي (GitHub Actions)
1. **تثبيت الإصدار:** ملف FVM/`flutter_version` مثبّت في المستودع = بناء قابل للتكرار حرفياً.
2. **مراحل CI عند كل push:** pub get → `flutter analyze` (سياسة صفر تحذيرات) → `flutter format --set-exit-if-changed` → `flutter test` (يشمل اختبارات التشكيل والحضور والأكسل) → build APK universal+splits → sha256 → **Release** بعنوان إصدار + changelog عربي + الأصول.
3. **K1 التوقيع:** المستودع خاص وبوت بلا صلاحية Secrets → نولّد keystore إصدار واحد **داخل المستودع الخاص** (موثق في README الأمني: غرضه توقيع تحديثات نفس التطبيق فقط، وكلمة مروره في متغير workflow بنفس المستودع). بديل أنظف لاحقاً إن منح مالك الحساب صلاحية Secrets.
4. **V1 تحقق أول تشغيل:** عند أول push نتأكد أن Actions ينطلق فعلاً على هذا المستودع؛ إن كان معطّلاً يطلب من مالك الحساب تفعيله من Settings مرة واحدة (خطوة وحيدة).
5. **اختبار دخاني اختياري (nightly):** emulator على CI لتشغيل سيناريو المسح الأساسي — لا يعرقل بناء كل push.
6. **ملصق توزيع:** كل Release يرفق QR بوستر (PDF) برابط تنزيل الـAPK لتعليقه بغرفة المعلمين.
